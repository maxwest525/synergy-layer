## 4. Risk statement

1. **Production is being updated from no source.** Since 2026-08-30 every merge to `synergy-layer` `main` has been live nowhere. Sixteen days of the backlog's "Verified 2026-08-31" and "2026-09-01" closures describe code that is not deployed. The operator has been publishing a stale mirror (three publish attempts per OP-10) and the docs told them the platform was the problem.
2. **Two repositories now claim the same project.** `PROJECTS.md` still says AOOS syncs to `synergy-layer`; Lovable says `trumove-resource-center`. Any session that reads `PROJECTS.md` will push to the wrong place and report success.
3. **Vercel adds a public origin and a second pipeline.** It cannot act on the database, but it renders a sign-in surface against production auth, builds a preview for every pushed branch, and its existence invites the assumption that it _is_ production. It also caused PR #102 and #103 to land in `main` to satisfy a host nobody has decided to use.
4. **The migration ledger is blind** to 30 of the 32 hand-named files. Re-running them by prompt can fail half-way and leave the schema in a state neither file set describes.

None of these is a security exposure by itself: RLS is on for all 89 tables, the Vercel shell has no service-role key, and the sign-in surface is the same one Lovable serves.

## 6. The long-term shape, and the decision it needs

Two facts decide it. Lovable holds the secrets, the custom domain, the Supabase project and the cron targets, and it works; moving production off it is a migration with seven moving parts and no evidence it is wanted beyond OP-8's one-line intention. And two repositories for one project is not a state anyone chose; it is what a re-link produced.

**Recommended:** one repository, connected to Lovable, with CI, PRs and Vercel (if kept) all pointing at it.

- **Option A — reconnect Lovable to `synergy-layer` — is not available.** Lovable's own documentation (docs.lovable.dev, "Git integration", read 2026-09-02) states that connecting a project "creates a new GitHub repository", that importing an existing repository is not supported ("You can only export from Lovable to GitHub"), and that on reconnect "Lovable creates a new repository with the current version of your project. The original repository stays unchanged on GitHub and is no longer linked." That is exactly the 2026-08-30 event: a disconnect and reconnect produced `trumove-resource-center` and orphaned `synergy-layer`. Disconnecting again would produce a third repository, not restore the first.
- **Option B — make `trumove-resource-center` canonical. This is the recommendation.** It needs no Lovable feature: merge as in step 2, re-link the Vercel project to it (or delete the project), move the open PR #91, and rename every reference in `PROJECTS.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`, the executor allowlist comments and the session prompts. `synergy-layer` becomes read-only history, archived on GitHub so nobody pushes to it by habit. Costlier in edits, zero platform risk, and it makes the Lovable-connected repository the one CI and every session already treats as the code of record.
- **Not recommended:** a mirroring GitHub Action from one repo to the other. It needs a PAT secret and adds a moving part whose failure mode is exactly the one just diagnosed: silent. Also not recommended: living with two repositories and a manual step 2 after every merge; that is the state that produced sixteen days of undeployed work.

**Vercel** should be either paused (reversible, one API call) or kept deliberately as a staging host with Vercel Authentication extended to production (an add-on on the Pro plan). Making it production would require, in order: every secret copied from the Lovable store into Vercel environment variables; `AOOS_PUBLIC_ORIGIN` set; the four pg_cron job URLs repointed by migration; the custom domain moved; `.well-known` and `/mcp` re-verified; and a full day of schedule firings observed. None of that has been started, and nothing in the evidence says it should be.
